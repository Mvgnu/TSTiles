## Archive: pass, including a narrow follow-up

**Reference:** official Protomaps PMTiles reader and CLI inspection workflow.
**Property:** reject unsuitable inputs, publish exact immutable bytes with
bounded resources, and retain a recoverable manifest without source edits.

The critic executed the built CLI and independently used official `pmtiles`
4.3.0 with a separate positional-file source. Input and published archive
header, metadata, and decoded tile matched. The fixture was 468 bytes with
SHA-256 `f3f65093582c81625cdfab11b3d1a27c2fb6aadcf8bd9802b2ad694d4d7cdca5`.
Decoded tile 0/0/0 was 49 bytes, one polygon, SHA-256
`9b25c6726af16561c00725a7a99eccde9104abbf727a27efde77005ceddcc79f`.

Plain text, truncation, v2, raster tile type, unsupported compression, and
missing attribution failed specifically. Repeating publication reused the
archive without changing its inode/mtime. A corrupted preexisting digest file
was refused without overwriting it or the prior manifest.

The critic killed publication of a synthetic 256 MiB archive after observing
16 MiB of temporary output. The old manifest and archive survived. A retry
completed with a matching full-file digest; observers saw only complete old
or new manifests. A 32 MiB declared compressed metadata section hit the
16 MiB read guard. A separate repeated-publication run peaked at 112,800 KiB
RSS (about 110.2 MiB) on that 256 MiB synthetic workload. This is evidence for
the exercised streaming path, not a planet-scale benchmark.

A later PM consistency check found that publication accepted style URL
fragments which the browser rejected. After the bounded correction, the same
independent critic exercised relative/absolute fragments: both failed before
any existing output changed or any new destination was created. Valid relative
and absolute style URLs with query strings remained intact.

**Final inspected archive artifacts:**

- CLI: `c16cef57909620d59c1d2397615fe49cbe8c133b38fbf1a9cd236e751301a425`
- API: `fe5dbe4308e74f752bcb24350813fbdd6719f084bda2f543f01986c4636640d4`

## Hosting: pass for native static HTTP

**Reference:** Caddy `file_server` and Protomaps static hosting guidance.
**Property:** serve, update, and roll back one archive with correct ranges and
cross-site access using one static server and no application database.

The critic started a separate Caddy instance and made 49 live protocol probes.
Exact 127-byte, interior, suffix, and open-ended ranges matched source bytes;
HEAD had no body; archive bytes were not HTTP-encoded. ETag/date conditions,
304/412/416, error `no-store`, CORS preflights, immutable archives, mutable
manifests, and private/path-traversal/directory probes behaved as specified.
Actual sockets bound only loopback; nonloopback connections were refused.

The critic published a second fixture archive, verified it before changing the
manifest, staged the pointer privately, and activated it by rename. The old
and new archives both remained readable. Rolling the manifest back restored
its exact previous bytes while Caddy stayed running. No source edit or
request-time application/database was required.

Shared route configuration SHA-256:
`49380054e63e0411e4dc234d2d56f904f4f1b00f7aa3881934440bc7e88a96a2`.

**Argument for pass:** actual protocol behavior and the release/rollback drill
matched the reference and could be performed from the documented operations.
Native Caddy HTTP is the supported evidence; Docker/TLS/S3 are not implied.

## Web: failed first round, passed independent reinspection

**Reference:** official Protomaps MapLibre PMTiles example, separately rendered
with the same fixture. **Property:** visible, interactive, attributed maps on
phone/desktop and a second site through configuration alone.

The first critic actually rendered the page at 1440×900 and 390×844; visible
polygon, attribution, pan/zoom, independent map instances on another origin,
iframe mode, and a supplied style with an unrelated GeoJSON source worked.
The reference comparison was explicit rather than blind A/B because interfaces
and labels differed.

**Single largest gap:** empty supplied styles and nonexistent source layers
produced a blank canvas while announcing `Map loaded`. One empty-style case
made no PMTiles request at all. This round failed despite green unit tests.

The builder changed ready-state evidence: drawing layers with no features
produce an actionable empty state; a style with no drawing layers produces an
error; non-queryable raster/terrain/background content remains intact and gets
`Style only`, not a claim that the vector archive rendered. A compatible
vector/GeoJSON style still requires visible features before `Map loaded`.
The PM's actual-browser regression reproduced the failure, then passed after
the change. The independent critic then reopened the actual served artifacts
and repeated the failed cases on desktop and phone. Empty style was `error`,
wrong layer was `empty`, and neither constructor emitted `ready`. Messages,
attribution, reset, and retry remained visible without horizontal overflow.

A compatible supplied style still displayed the fixture and its unrelated
GeoJSON point. The full style URL and query string, both sources, and per-map
interaction remained intact. Real diagnostic raster, DEM/terrain/hillshade,
and background content rendered unchanged, with `Style only` rather than false
success or a false broken-map error. The critic inspected actual screenshots,
network traces, constructor status histories, and rendered features.

**Argument for pass:** valid configured maps render and interact independently
on another origin, while the formerly false-success cases now have honest,
actionable outcomes. This closes the single largest gap of the first round.
